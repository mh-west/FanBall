# 서버 기반 양 팀 동시 작전 투표 및 홈 경기 목록 설계

작성일: 2026-11-05  
상태: 서버 투표 기반 코드와 UI 연결을 추가했다. Supabase 프로젝트에 migration/함수를 적용하고 공식 경기 오케스트레이터를 연결하기 전까지 실사용 투표는 비활성이다.

## 제품 동작

### 양 팀 작전 투표

- 작전 투표가 필요한 상황이면 서버가 타석별 라운드 하나를 연다.
- 공격팀 팬에게는 공격 작전, 수비팀 팬에게는 수비 작전이 동시에 표시된다.
- 두 역할은 같은 서버 `closes_at`을 쓰며, 어느 한쪽이 먼저 투표를 끝내도 창은 닫지 않는다. 두 역할 모두 똑같이 15초 동안 선택한다.
- 경기 당사자가 아닌 응원팀 팬은 선택 카드 대신 `작전 선택 중입니다`와 같은 남은 시간을 본다. 로그아웃 또는 응원팀 미설정 사용자도 관전할 수 있다.
- 로그인 사용자는 자기 계정·응원팀 역할에 한 표를 낸다. 마감 전 수정은 허용한다. 라운드 시작 시 응원팀을 고정해 투표 중 팀을 바꿔 양쪽에 참여하지 못하게 한다.
- 마감 시 서버가 역할별 다수 선택을 확정한다. 동률/무표 역할은 해당 역할의 기본 작전을 적용한다. 선택별 득표수는 종료 뒤 공개하고, 투표 중에는 참여자 수만 공개하는 방식을 제안한다.
- 두 작전이 모두 확정된 뒤 결합 확률 계산과 공식 타석을 한 번 진행한다. 세 사용자 유형(공격 팬, 수비 팬, 관전자)은 같은 최종 결과를 받는다.

### 메인 경기 목록

- 메인 화면은 오늘 일정에 편성된 KBO 경기를 전부 목록으로 보여준다. 통상 5경기 편성일에는 5경기가 모두 보인다.
- 실제 일정이 5경기보다 적은 날에는 실제 경기만 표시하고, 휴식일에는 빈 상태 문구를 표시한다. 가짜 일정을 실제 일정처럼 채우지 않는다.
- 경기 카드에는 원정/홈 구단, 시작 시각, 팬볼 준비/투표/진행/종료 상태, 내 응원팀의 투표 역할을 보여준다.
- 진행 중 카드에는 이닝 초·말, 점수, 공격팀, `작전 선택 중입니다` 또는 내 팀 작전 UI 상태를 표시한다.
- 각 공식 팬볼 경기는 `kbo_game_id`로 유일하게 연결한다. 현재 샘플 일정은 실제 KBO 일정과 혼동되지 않도록 표시한다.

## 구현 구성

1. 웹 클라이언트는 경기 목록·상세 화면을 보여주고 Supabase Realtime으로 공개 상태를 구독한다. 표 제출은 검증된 RPC로만 한다.
2. Supabase Auth는 사용자 ID를 제공하고 `profiles.favorite_team_id`에 응원팀을 보관한다. Google OAuth 설정 절차는 `docs/AUTH_SETUP.md`를 따른다.
3. Postgres는 일정·팬볼 경기·투표 라운드·작전·표·확정 결과를 저장한다. RLS는 직접 쓰기를 막고 RPC만 표를 변경하도록 한다.
4. 서버 함수/스케줄러는 마감 및 확정을 처리한다. 브라우저가 닫혀도 15초가 지나면 마감되어야 한다.
5. 공식 엔진은 서버가 저장한 타석 상태, 두 작전, 기록/모델 버전, 시드를 입력으로 받는다. 클라이언트가 보낸 결과는 신뢰하지 않는다.

Supabase Free는 MVP의 Auth/Postgres/Realtime 후보지만 무료 사용량과 cron 실행 제한은 배포 시점에 확인한다. 서버가 18시 운영과 여러 경기를 보장해야 한다. 무료 cron이 적합하지 않으면 재시도 가능한 별도 스케줄러를 검토한다.

## 데이터 모델 제안

| 테이블 | 핵심 필드 | 제약/용도 |
|---|---|---|
| `profiles` | `user_id`, `nickname`, `favorite_team_id` | Auth 사용자별 프로필 |
| `kbo_games` | `id`, `game_date`, `scheduled_at`, `away_team_id`, `home_team_id`, `status`, `provider` | 공급원 경기 ID 고유, 실제 일정과 데모 분리 |
| `fanball_games` | `id`, `kbo_game_id`, `status`, `inning_state`, `score`, `seed`, `model_version` | `kbo_game_id UNIQUE`로 공식 팬볼 한 경기 보장 |
| `fanball_game_memberships` | `game_id`, `user_id`, `team_id`, `joined_at` | `UNIQUE(game_id,user_id)`, 경기별 응원팀 스냅샷. 프로필 팀을 바꿔도 해당 경기 역할은 고정 |
| `tactical_rounds` | `id`, `fanball_game_id`, `pa_no`, `state_snapshot`, `offense_team_id`, `defense_team_id`, `opens_at`, `closes_at`, `status` | 한 타석의 투표 창과 공통 서버 마감 |
| `tactical_choices` | `id`, `round_id`, `role`, `choice_key`, `label`, `is_default` | 역할별 허용 선택지 |
| `tactical_votes` | `round_id`, `user_id`, `role`, `team_id`, `choice_id`, `updated_at` | `UNIQUE(round_id,user_id)`, 마감 전 upsert |
| `tactical_resolutions` | `round_id`, `offense_choice_id`, `defense_choice_id`, `vote_counts`, `tie_or_default`, `model_version` | `round_id UNIQUE`, 변경 불가한 개표 결과 |
| `plate_appearances` | `game_id`, `pa_no`, `round_id`, `outcome`, `runs`, `distribution`, `seed_fragment` | `UNIQUE(game_id,pa_no)`로 타석 중복 실행 방지 |

시간은 `timestamptz` UTC로 저장하고 화면에서 KST로 표시한다. 실제 migration에서 FK와 범위 제약을 추가한다.

## 투표 RPC: `submit_tactical_vote(round_id, choice_id)`

경기 페이지 진입 시 서버가 Auth의 `auth.uid()`와 프로필 응원팀을 `fanball_game_memberships`에 최초 1회 저장한다. 이 스냅샷은 해당 경기에서 바뀌지 않는다. 표 제출 RPC는 이 경기별 팀 소속과 라운드의 공격/수비 팀을 비교해 역할을 계산한다. 한 DB 트랜잭션에서 라운드 행을 잠그고 서버 시각이 `closes_at`보다 이른 `open` 라운드인지 검사한다. 클라이언트가 보낸 팀/역할은 신뢰하지 않는다. 선택지가 그 역할에 허용됐는지 확인하고 `(round_id,user_id)`를 upsert한다. 이미 표가 있는 경우 역할·팀은 유지하고 선택지만 수정한다. 재투표는 마감 전까지만 허용한다. 투표별 선택값은 마감 전 다른 사용자에게 공개하지 않는다. 유효하지 않은 팀/작전, 만료 라운드, 비로그인 쓰기는 거절한다.

## 마감 함수: `resolve_tactical_round(round_id)`

1. 라운드를 잠근다. 이미 완료된 라운드라면 저장한 결과를 그대로 반환한다.
2. 마감 전 실행을 거절한다. 마감 이후 `open`을 `closing`으로 바꿔 신규 표를 차단한다.
3. 양 역할의 표를 집계하고 최다 득표를 확정한다. 동률/무표는 역할별 기본 작전이다.
4. `tactical_resolutions`에 라운드당 하나만 저장한다.
5. 두 확정 작전을 고정된 타석 입력에 결합하고 서버 경기 엔진을 한 번 실행한다.
6. `plate_appearances`의 고유 제약을 사용해 결과를 저장하고 라운드를 완료한다.
7. Realtime으로 확정 작전과 타석 결과를 모두에게 알린다.

마감 함수 재시도, 서버 재시작, 클라이언트 재접속에도 공식 타석을 중복 실행하지 않는다. 결과 저장·라운드 완료·다음 경기 상태 이동은 트랜잭션/상태 머신으로 원자성을 보장한다. `closing` 실패는 재시도 큐가 이어받고 표는 다시 받지 않는다.

## 사용자별 UI 상태

| 상황 | 표시 |
|---|---|
| 응원팀이 공격팀 | `공격 작전 선택`, 공격 선택지, 공통 15초 카운트다운 |
| 응원팀이 수비팀 | `수비 작전 선택`, 수비 선택지, 같은 마감 카운트다운 |
| 다른 팀 응원 | 선택지 대신 `작전 선택 중입니다`, 같은 카운트다운 |
| 미로그인/응원팀 미설정 | 관전 가능, 참여를 위한 로그인/응원팀 안내 |
| 투표 완료 | 내 선택과 수정 가능 상태, 마감까지 남은 시간 |
| 마감 후 | 양측 확정 작전과 득표 요약, 동일한 공식 타석 결과 |

어느 한쪽이 먼저 표를 냈다고 타이머를 닫거나 다음 타석으로 넘어가지 않는다. 전 클라이언트가 라운드의 동일한 `closes_at`을 구독한다.

## 보안 및 예외 처리

- 브라우저는 역할, 마감, 득표 결과, 공식 타석 결과를 확정할 권한이 없다.
- 관리자 초기화/개발 실행은 별도 서버 권한으로 보호한다. `?admin=1`만으로 DB 권한을 주지 않는다.
- 행 잠금, 고유 제약, idempotency key로 재투표·마감·타석 진행을 직렬화한다.
- 한 역할에 표가 없어도 15초 창을 유지하고 빈 역할은 기본 작전을 사용한다.
- Realtime이 끊긴 클라이언트는 RPC로 상태를 다시 조회한다. 클라이언트 시계가 아니라 서버 시각을 기준으로 제출 허용 여부를 판단한다.
- 우천 취소·연기 경기의 투표를 열지 않고 일정 상태/사유를 표시한다.

## 구현 단계

1. Supabase 프로젝트/Auth와 DB 사용자 프로필을 연결한다.
2. 오늘 KBO 일정 공급 인터페이스를 만들고 메인에 일정 전체를 표시한다. 공급원 연결 전에는 5개 카드가 데모임을 명확히 표시한다.
3. migration/RLS 및 라운드·선택지·표·확정 결과 테이블을 만든다.
4. 제출 RPC와 서버 마감 함수를 구현한다.
5. 공격 팬·수비 팬·관전자 계정 세 개로 동일 15초, 역할 제한, 동률/무표, 재접속, 중복 요청을 검증한다.
6. 서버 엔진 입력/확률 모델 버전과 확정 결과를 보존한다.
7. 더블헤더, 취소, 변경된 경기 시각, 하루 5경기 목록을 검증한다.

## 보류할 정책

- 기본 제안은 역할별 최다 득표, 동률/무표 시 기본 작전이다.
- 마감 전 수정 허용, 선택별 득표수는 종료 후 공개, 투표 중 참여자 수만 공개를 제안한다.
- 공식 KBO 일정에 편성된 경기를 전부 표시한다. 통상 5경기일에는 5개지만, 일정이 적거나 없는 날에는 가짜 경기를 만들지 않는다.

## 구현 상태와 남은 범위

저장소에는 migration/RLS/RPC, 서버 전용 라운드 개설·마감 Edge Function, 프런트의 서버 상태 조회·투표 제출 UI가 추가되었다. 함수는 서버 기준 15초 창을 만들고 역할별 표를 집계하도록 작성했지만, Supabase 프로젝트 연결과 migration 적용, 함수 배포가 아직 없어 실사용 투표는 동작하지 않는다.

또한 공식 경기 오케스트레이터가 아직 없다. 즉, 현재 코드만으로 경기 상태를 서버에서 만들거나 실제 타석을 멈추고 확정 작전을 엔진에 반영하지 않는다. 실제 KBO 일정 공급원도 연결 전이다. 홈 화면은 일정 테이블이 비어 있거나 설정이 없으면 명확히 테스트 일정 5개를 표시한다. 완료된 공식 경기 결과는 현재 로컬 데모 엔진에서만 생성된다.
